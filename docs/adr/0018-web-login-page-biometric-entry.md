# web 登入頁提供 Face ID／指紋的「開啟」入口：意圖走授權請求，憑證仍只在手機

補充 [ADR-0017](0017-biometric-login-stays-on-device.md)，不推翻它（ADR-0017 已由 [ADR-0019](0019-logout-revokes-biometric-login-only-while-signed-in.md) 取代）：生物辨識與憑證仍只在手機上，後端不存 passkey 或任何憑證。ADR-0017 的「登入頁入口」只涵蓋 App 內的登入畫面；歡迎頁的登入鈕直接開瀏覽器後，使用者沒有地方第一次開啟，只能登入後去設定頁。本 ADR 讓使用者在 **web 登入頁**就能開啟，並規定已開啟後的路徑與設定頁的開關。

## Decision

- **已開啟後直接解鎖，不開任何登入頁**：手機有保留憑證時，歡迎頁的登入鈕直接跳生物辨識解鎖並進入 App，不顯示 App 登入畫面，也不開瀏覽器。冷啟動維持現狀：讀憑證時由系統跳生物辨識。解鎖取消或失敗時留在歡迎頁，按「登入」再解鎖一次。歡迎頁是唯一的登入入口，App 內不再有獨立的登入頁；舊的 `/login` 連結（驗證信、邀請、分享）轉址到歡迎頁並保留原本要去的地方。
- **web 登入頁不處理「已開啟」情境**：使用者會到 web 登入頁，代表直接解鎖已失敗（取消、憑證被撤銷、生物特徵變更）或本來就沒開啟。所以 web 登入頁的生物辨識鈕只有一個意思：**用這組帳密登入，並開啟生物辨識登入**。帳密一律必填，不看手機有沒有保留憑證。
- **按鈕位置**：登入鈕下方，隔一條「或」，描邊的次要按鈕（比較頁選項 A）。名稱寫出實際驗證方式：App 發起授權時帶 `Face ID`／`Touch ID` 提示，沒帶用「生物辨識」。
- **只在 App 發起的授權顯示**：授權請求的顯示資料多一個「來自 App」的旗標；用電腦瀏覽器直接開登入頁（沒有授權請求）時不顯示。
- **開啟的流程**：按專門鈕時，web 照常登入，並在授權請求上記下「要開啟」；成功導回 App 時，由 server 在網址加旗標。App 看到旗標，先通過一次生物辨識，再把憑證改成生物辨識保護；取消只是沒開啟，登入照常完成。旗標只由專門鈕帶出，一般登入鈕不帶；旗標不含憑證，偽造也開不了，因為開啟一定要在手機上通過生物辨識。
- **設定頁開啟與關閉都要重新驗證密碼，且走 web 頁面**：App 發起授權，要求 web 強制重新輸入密碼（`prompt=login`），並在授權請求上記下意圖（開啟或關閉）；登入帳號必須與目前帳號相同，否則拒絕。導回 App 後，App 先通過一次生物辨識，再套用：開啟＝改成生物辨識保護；關閉＝清除憑證與金鑰並登出。帳號不符時 api 不發授權碼，導回 App 並帶 `error=reauth_account_mismatch`，App 提示「登入的帳號與目前帳號不同」且不改任何狀態。單獨 `prompt=login`（沒有生物辨識意圖）也強制重新輸入密碼。取代現行「只驗生物辨識」的開啟與關閉。
- **回 App 的網址仍只由 server 組**：沿用 `authorize-requests` 的規則，web 不能傳入任何 URL 或參數；旗標由 server 依授權請求上記的意圖加入。
- **解除**：沿用 ADR-0017。「關閉生物辨識登入」「忘記這支手機」清除憑證；使用者變更密碼時，後端撤銷其他登入憑證，手機的保留憑證於下次 refresh 被拒時清除、入口消失；重設密碼撤銷全部。
- **共用手機換帳號**：沿用 ADR-0017，不同帳號登入前先清掉前一個人保留的憑證。
- **手機沒有 Face ID／Touch ID（只有裝置密碼）**：App 不當成錯誤，照常登入，回 App 後提示「這支手機沒有設定 Face ID／Touch ID，已用一般方式登入」，不開啟。

## Considered Options

- **只在 App 端做（歡迎頁先到 App 登入頁再顯示入口）**：不動 web 與 api，改動最小。拒絕：owner 要求入口在 web 登入頁。
- **web 登入頁區分「已開啟」與「第一次」，已開啟時按鈕導回 App 解鎖**：需要「手機有保留憑證」提示與不需登入的導回端點。拒絕：已開啟時 App 已直接解鎖，不會到 web 登入頁，這一支路徑用不到。
- **登入成功後 App 再詢問是否開啟（舊版 0.36 做法，現行 `answerPrompt`）**：不用旗標。保留作為補充，但入口不在登入頁，不符合要求。
- **設定頁只驗生物辨識就能開關（現行）**：拒絕：owner 要求開啟與關閉都要重新驗證密碼。
- **passkey（ADR-0016）**：拒絕理由同 ADR-0017，要後端存憑證。

## Consequences

- **api 要新增三件事，都不存憑證**：授權請求的顯示資料帶「來自 App」旗標與按鈕名稱提示；授權請求可記下意圖（開啟、關閉）並在導回時由 server 加旗標；實際處理 `prompt=login`，並在設定頁的重新驗證中確認帳號相同。這與 ADR-0017「後端不新增任何東西」的字面不同，後者指的是憑證與資料表，這裡只是授權請求多幾個欄位。
- **`prompt=login` 由伺服器端強制**：批准時要求這個 bearer 是「登入後 60 秒內由 `/api/oauth/login` 簽發」；限制：超過 60 秒要重新登入，且 60 秒內 refresh 出來的新 token 仍共用同一個 grant，也會通過（需先有密碼登入）。這不是伺服器再驗一次密碼。iOS 與 Android 授權視窗的實際行為未經真機驗證。
- **導回的旗標能否可靠到達 App 尚待真機驗證**：登入成功導回 App 時網址多一個參數，iOS ASWebAuthenticationSession 與 Android Auth Tab 都要確認參數不會被吃掉。
- **0.40.1 的「歡迎頁先到 App 登入畫面再按 Face ID」已改為直接解鎖**；0.41.1 起 App 內沒有獨立的登入頁。冷啟動讀受保護憑證時系統本身就會跳一次驗證，所以不另做「冷啟動自動解鎖」。
- web 登入頁多一顆按鈕，屬版面改動，按 web 規定要先 `/prototype` 並由 owner 簽核；已簽核選項 A。
- 三個倉庫（api、web、Flutter）要協調發版，順序是 api → web → App；舊版 App 不帶來源資料時，web 不顯示專門鈕。

## 為何難以逆轉

api 的授權請求欄位與旗標，以及 App 對旗標的處理，一旦上線，舊版 App 與 web 之間就有了依賴；撤掉需要版本協調。使用者也會預期「設定頁開關要輸入密碼」。
