# web 登入頁提供 Face ID／指紋入口：訊號走授權請求，憑證仍只在手機

補充 [ADR-0017](0017-biometric-login-stays-on-device.md)，不推翻它：生物辨識與憑證仍只在手機上，後端不存 passkey 或任何憑證。ADR-0017 的「登入頁入口」只涵蓋 App 內的登入畫面；歡迎頁的登入鈕直接開瀏覽器後，使用者看不到入口，也沒有地方第一次開啟。本 ADR 把入口補到 **web 登入頁**。

## Decision

- **入口在 web 登入頁**：App 發起的授權，web 登入頁有專門的「用 Face ID／Touch ID 登入」鈕，與一般登入鈕分開。只有 App 發起的授權才顯示；用電腦瀏覽器直接開登入頁時不顯示。
- **App 發起授權時帶一個提示**：這支手機有沒有保留的生物辨識登入憑證。api 把它存在授權請求上，web 讀授權請求時一併拿到。它只決定 web 要不要擋空欄位，不授予任何權限。
- **手機有保留憑證**：按專門鈕，帳密不必填。web 呼叫導回端點，授權請求作廢，視窗導回 App 並帶 `error=biometric_requested` 與 `state`；App 跳生物辨識，通過就用保留的憑證登入。
- **手機沒有保留憑證**：按專門鈕，帳密必填。web 照常用這組帳密登入，並在授權請求上記下「要開啟生物辨識登入」；成功導回 App 時，由 server 在網址加旗標。App 看到旗標，先通過一次生物辨識，再把憑證改成生物辨識保護；取消只是沒開啟，登入照常完成。
- **旗標只由專門鈕帶出**：一般登入鈕不帶。旗標不含憑證，偽造也開不了，因為開啟一定要在手機上通過生物辨識。
- **回 App 的網址仍只由 server 組**：沿用 `authorize-requests` 的規則，web 不能傳入任何 URL 或參數；導回端點只會導向授權請求上已驗過的 `redirect_uri`，單次使用、有限流。
- **解除**：沿用 ADR-0017。「關閉生物辨識登入」「忘記這支手機」清除憑證；使用者變更密碼時，後端撤銷其他登入憑證，手機的保留憑證於下次 refresh 被拒時清除、入口消失；重設密碼撤銷全部。
- **共用手機換帳號**：沿用 ADR-0017，不同帳號登入前先清掉前一個人保留的憑證。
- **手機沒有 Face ID／Touch ID（只有裝置密碼）**：App 不當成錯誤，照常登入，回 App 後提示「這支手機沒有設定 Face ID／Touch ID，已用一般方式登入」，不開啟。

## Considered Options

- **只在 App 端做（歡迎頁先到 App 登入頁再顯示入口）**：不動 web 與 api，改動最小。拒絕：owner 要求入口在 web 登入頁，使用者實際停留的地方。
- **web 不知道手機狀態，按了再讓 App 決定、必要時重開視窗**：api 不用存提示。拒絕：沒有憑證時要多開一次視窗，使用者已填的帳密還要重輸入。
- **登入成功後 App 再詢問是否開啟（舊版 0.36 做法）**：不用旗標。拒絕：入口不在登入頁，不符合要求。
- **passkey（ADR-0016）**：拒絕理由同 ADR-0017，要後端存憑證。

## Consequences

- **api 要新增三件事，都不存憑證**：授權請求存並回傳「手機有保留憑證」提示；不需登入的導回端點（單次使用、有限流）；登入時記「要開啟」並在導回時加旗標。這與 ADR-0017「後端不新增任何東西」的字面不同，後者指的是憑證與資料表，這裡只是授權請求多幾個欄位與一個端點。
- **「授權視窗能否在沒有授權碼時被導回 App 並關閉」尚未驗證**：iOS ASWebAuthenticationSession 與 Android Auth Tab 都要真機試過，才能開工；若不成立，本 ADR 作廢。
- web 登入頁多一顆按鈕，屬版面改動，按 web 規定要先 `/prototype` 並由 owner 簽核。
- 三個倉庫（api、web、Flutter）要協調發版，順序是 api → web → App，舊版 App 不帶提示時 web 不顯示專門鈕。

## 為何難以逆轉

api 的授權請求欄位與導回端點，以及 App 對 `biometric_requested` 與旗標的處理，一旦上線，舊版 App 與 web 之間就有了依賴；撤掉需要版本協調。
